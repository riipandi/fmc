## Settings, themes, and keys from files — a Settings page, a theme catalog, and a keymap file, in six phases

### Objective

The owner asked for three things that share one config folder: the saved settings (RI-9), a theme catalog (RI-10), and a keymap file (RI-13), and on 2026-11-27 a Settings page opened with `Ctrl+,`. This plan orders them so each phase ships alone: the settings file gets a safe write path first, then the theme mode and the catalog, then the page that edits the settings, then the keymap file. The tree after phase 5 has the settings written by the page, `~/.config/fmc/themes/*.json` read at start, `~/.config/fmc/keymap.json` read at start, and every default key unchanged. The plan does not open writes to themes or the keymap, and it does not save UI state (sidebar width, wrap) unless D3 says so.

### Current state (verified in the tree, 2026-11-27, branch `docs/plan-00015-settings`)

- **The settings file is read once and never written.** `src/main.rs:49-50` loads it before the UI starts; `src/services/settings.rs:1-2` says the UI thread never reads it again; `src/services/settings.rs:21-31` `load` maps a missing file to the defaults and a read error to a notice. Nothing in `src/` writes `settings.json` (`grep -rn "fs::write\|File::create" src` finds only the write layer for files the user manages, `src/services/write.rs`).
- **The schema is six keys.** `src/settings.rs:9-13` defines `AUTO_PREVIEW`, `SIDEBAR_JUMP`, `READER_JUMP`, `GIT_GUTTER`, `FIND_MODE`; `src/settings.rs:16-22` is the `Settings` struct (`auto_preview`, `sidebar_jump`, `reader_jump`, `git_gutter`, `file_associations`, `find_mode`). `parse` (`src/settings.rs:47`) reads a `serde_json::Value`, so one bad value keeps its own default and a notice names it. Invalid JSON keeps every default (`src/settings.rs:47-62`).
- **Parse errors and notices reach the footer once at start.** `src/app/mod.rs:324-331` applies the values and sets `m.message` from `settings.notices`.
- **The UI state RI-9 names is not in the file.** Sidebar width and collapse, wrap (`Model.wrap`, `src/app/mod.rs`), split or unified and context lines (`src/keys/mod.rs` `ToggleSplit`, `ToggleContext`), and dotfiles (`ToggleDotfiles`) live only in memory.
- **The palette is fixed and its fields are borrowed strings.** `src/theme.rs:5-8` `Mode` (`Dark`, `Light`); `src/theme.rs:21-48` `Palette` has `&'static str` fields; `src/theme.rs:51` `DARK` and `:88` `LIGHT` are `const`; `src/theme.rs:125` `palette(mode) -> &'static Palette`. A JSON theme cannot be a `Palette` without an owned type or a leak. `src/app/mod.rs:210-212` `Model::palette` returns `&'static Palette`.
- **The terminal chooses the mode and nothing else.** `src/app/theme.rs:28` `watch` reads the background at start, every 3 s, and on the terminal's announcement; `src/app/mod.rs:343` calls it. No setting or key chooses the mode. `src/app/mod.rs:598-605` `restyle` rebuilds the colour-baked parts, so a theme change can repaint at once.
- **`Ctrl+,` is free, and so is plain `,`.** `src/keys/parser.rs:145-186` `global` binds `Ctrl+/` and `Ctrl+_` (`:163`), `Ctrl+f` in a prompt (`:165`), `Ctrl+.` (`:167`), and the plain `.` (`:178`); no arm names `,`. `src/keys/parser.rs:61-64` binds `Ctrl+q` and `Ctrl+c` to quit.
- **The key decoder is native, and the legacy encoding has no `Ctrl+,`.** The locked `opentui` 0.9.9 (`Cargo.lock`) translates a native record in `src/input/parser.rs:252-300` (`key`); the native parser is `packages/native/src/input-parser.zig` in the scratch checkout `/private/tmp/fmc-ref/opentui` (version 0.9.9, `packages/core/package.json:12`). Legacy control bytes map to Ctrl keys only for `0x00`, `0x01`-`0x1a` (except `0x08`, `0x09`, `0x0a`, and `0x0d`), and `0x1c`-`0x1f` (`input-parser.zig:489-491`): `0x2c` is the plain comma, so a legacy terminal cannot send `Ctrl+,` as a Ctrl key.
- **The kitty keyboard protocol sends `Ctrl+,`.** `opentui-0.9.9/src/host.rs:147` asks for `DISAMBIGUATE | ALTERNATE_KEYS` by default. A terminal that answers sends `CSI 44;5u`, which `input-parser.zig:1269-1300` `kittyKey` decodes to the code `,` with the Ctrl modifier. `Ctrl+.` (RI-12, `src/keys/parser.rs:167`) takes the same path, and its roadmap note names Ghostty, Rio, kitty, and WezTerm as the terminals that send it and Terminal.app as the one that cannot (`roadmap-00001-post-parity.md`, RI-12). Not re-checked here: the terminal list and Terminal.app. The owner check of RI-12 is still open.
- **The key "table" is help text, and dispatch is code.** `src/keys/mod.rs:118` `KEY_SECTIONS` holds the rows for `?` and `--help`; `src/keys/parser.rs:145-254` dispatches with `match` arms. `src/keys/tests.rs:228` `every_documented_key_is_bound` and `:265` `the_key_page_and_help_come_from_the_key_table` tie the two by test. RI-13 and `architecture.md` ("Keys are dispatched from one key table") describe a table that dispatch reads; the tree has none. Phase 4 makes that true.
- **The overlay machinery can host a field.** `src/overlay.rs:92-104` `Dialog` has a title, a message, an optional field, buttons, and an error line; `src/ui/dialog.rs` draws it; `src/app/overlay.rs:197` `open_dialog` opens it. The menu (`src/overlay.rs:9-27` `Item`, `Menu`) picks and closes, so it cannot show a value per row.
- **OpenTUI 0.9.9 has no checkbox, switch, or modal widget.** Its widgets are `Select` (rows with a name and a description, `opentui-0.9.9/src/widget/select.rs:11-19`), `TabSelect` (`src/widget/tabs.rs:13`), `Input`, `Slider`, `Table` (`src/widget/table.rs:11`), and `Textarea`. `Select` has no disabled row, and a click on an unselected row only moves the selection (architecture.md, "The context menu and the dialog"). fmc builds its own dialog and menu, as the existing record says.
- **The bundled theme catalog's source has 16 themes, not the 13 RI-10 lists.** `bjarneo/editor` `src/theme.rs` (fetched 2026-11-27, `main`) has 9 dark and 7 light built-ins (`BUILTINS`, lines 53-210), each with 24 colour roles (`Builtin.hex`, line 47) and a `light` flag. RI-10 omits `rose-pine` (Rosé Pine), `rose-pine-dawn` (Rosé Pine Dawn), and `light` (editor light). Its licence is MIT, `Copyright (c) 2026 The editor authors` (`LICENSE`, fetched 2026-11-27).
- **The bjarneo roles map to 17 fmc values, and 10 fmc tokens have no source value.** Mapping in the table under Decisions (A9). Roles `bg2` (1), `vis` (9), `cmd` (10), `ty` (15), `mac` (16), and `prop` (19) have no fmc token.
- **`serde_json` is a dependency with no `preserve_order`, and `serde` is not declared.** `Cargo.toml` has `serde_json = "1.0.154"` and no `serde`. A `serde_json::Map` is a `BTreeMap` without `preserve_order`, so a rewritten file sorts its keys (`architecture.md`, "Approved deviation: `file_associations`": "serde_json keeps no file order"). `rules.md` ("Approved for after parity") approves `serde` with `derive` and `serde_json` for RI-9 and RI-10; the architecture record of the read-only settings says `serde_json` alone is enough.
- **Scouter has no configuration and fixed palettes.** `scouter:docs/decision/0001-read-only-and-minimal.md:7` ("no configuration file"), `scouter:src/ui/theme.ts:115-127` (`palettes: { dark, light }`, and `setThemeMode`), `scouter:src/app/app.ts:202` (the mode comes from the terminal only), `scouter:src/core/keymap.ts:3-55` (the fixed key list). The baseline is v0.3.4, `434d000f` (`rules.md`, "Baseline"). The local Scouter checkout is `/private/tmp/fmc-ref/scouter` at `434d000`; `grep -rn ","` in its `src/` finds no comma binding.
- **Writes are closed except for the file manager.** `AGENTS.md` ("Writes are bounded") and `rules.md` ("Writes", the third bullet) say fmc never writes its own settings. `architecture.md:477-481` (plan-00012 D10) keeps "fmc's own settings" read-only, and `docs/configuration.md:3` and `:53` and `docs/parity.md:40` say the file is never written.
- **A symlinked settings file is common for dotfile setups.** Nothing in the tree handles one; `services/write.rs` treats a link as the entry (`rules.md`, "Writes", the third bullet), which is the rule for the user's files, not for fmc's own.

### Owner decisions (answered 2026-11-27)

**Answers (owner, 2026-11-27):** every recommendation, D1 to D16, with one change: D12 binds `Ctrl+,` only. No plain `,` and no `:settings`; a terminal without the kitty protocol has no route to the page (accepted by the owner). The owner approved the plan and every phase in order in the same message.

Each item gives the options, the recommendation first where one exists, and the cost of the wrong pick. The owner answers each as a number and a word, for example "D1 a, D2 a, D4 a".

- **D1 — the write rule.** Options: (a) open writes to `settings.json` only, in `$XDG_CONFIG_HOME/fmc/` (`src/services/settings.rs:12-18`); themes and the keymap stay read-only [recommended: RI-9 names this file, and the phase 1 undo is one commit]. (b) Open writes to the whole config folder, so the page could also write theme and keymap files. (c) Keep the rule, drop saving from RI-9, and the page edits nothing on disk. A wrong pick under (b) means fmc writes files the owner did not name; under (c) RI-9's saved settings never land. Cost of (a): `AGENTS.md` ("Writes are bounded"), `rules.md` ("Writes" and "Parity with Scouter", the third bullets), and `architecture.md:477-481` change in phase 1.
- **D2 — what the Settings page edits.** Options: (a) the settings keys only: `auto_preview`, `sidebar_jump`, `reader_jump`, `git_gutter`, `find_mode`, `theme_mode`, `dark_theme`, `light_theme` [recommended]. Numbers open the existing dialog's field (`src/overlay.rs:92`), so they need no new widget. (b) (a) plus the keymap (in-UI rebinding), which D11 defers. (c) Enums and toggles only; numbers stay hand-edited.
- **D3 — saved UI state.** RI-9 says fmc "remembers the UI state the user changes": sidebar width and collapse, wrap, split or unified, context lines, dotfiles. Options: (a) not in this plan: the file keeps the settings keys only [recommended: each of `w`, `s`, `x`, `Ctrl+/`, and `.` would write the file, which needs its own decision, and RI-9 stays `landed in part` for it]. (b) Save each UI change at once. (c) Save on quit only (a crash loses the change).
- **D4 — page or dialog.** Options: (a) a full page in the content area, like the changes screen, and a `Pages` page in the compact tier (`src/app/pages.rs`) [recommended: eight to nine rows with a value and a one-line help do not fit a 16-row menu or a 3-button dialog]. (b) A dialog-sized overlay built on the menu, which closes on a pick, so a value could not stay on screen. Wrong pick under (b): the page cannot show the values it edits.
- **D5 — when a change saves and applies.** Options: (a) Enter or Space changes the value, saves it at once, and applies it at once; a theme row repaints the UI, so the change is its own preview [recommended: `restyle` already repaints, `src/app/mod.rs:598`]. (b) Preview on move, Esc reverts, Enter saves. (c) A Save row at the end. Under (b) the page needs a revert path for every row; (a) needs none.
- **D6 — how a theme is picked.** Options: (a) `theme_mode` (`auto`, `dark`, `light`), `dark_theme`, and `light_theme` (catalog ids). `auto` follows the terminal (`scouter:src/app/app.ts:202`) and picks the id for the mode it found [recommended: bjarneo's own `resolve(source, dark_id, light_id, system_dark, omarchy)` (`bjarneo/editor` `src/theme.rs:389`) uses this model]. The default id is `scouter`, the existing `DARK` and `LIGHT`. (b) One `theme` id, and the theme's own `mode` decides; `auto` then chooses only between the Scouter pair. Wrong pick under (b): a dark terminal cannot pair a dark and a light theme.
- **D7 — where user themes live and how they win.** Options: (a) `~/.config/fmc/themes/<id>.json` is read at start, the id is the file name, the bundled catalog is compiled into the binary in the same format, and a user file with a bundled id replaces it [recommended: works offline, and the bundled files test the parser]. (b) Seed the themes folder with the bundled files on first run. Seeding writes outside the settings file, so it needs D1 (b).
- **D8 — the theme file's format.** Options: (a) the 32 colour values fmc paints with (`src/theme.rs` `Palette`, its six syntax entries, the three wordmark colours), all required; a file missing one is skipped with a notice that names it. (b) The 24 roles bjarneo uses (`bg` … `on`) plus `mode`, and fmc derives the 32 values through the mapping in A9 [recommended: a bjarneo theme pastes in unchanged, and the bundled and user files share one shape]. Cost of (b): the derived values (A9, the "no source value" rows) are fmc's choice, not the theme author's, and every derived value needs a contrast check.
- **D9 — the theme's background.** fmc paints the terminal background tinted 2.5 % toward white or black (`src/theme.rs:150-160`, `scouter:src/ui/theme.ts:145` `tintedBackground`). Options: (a) keep that; a theme's `bg` is only the fallback when the terminal does not answer [recommended: every theme keeps Scouter's look under the terminal's own background]. (b) Paint the theme's `bg`. Under (b) each catalog theme changes the page's background, a visible deviation needing its own record.
- **D10 — JSON or JSONC.** Options: (a) strict JSON for `settings.json`, `keymap.json`, and theme files [recommended: `serde_json` parses it with no new code; a save rewrites `settings.json`, and a rewrite drops comments, so a commented file the page saves would lose its notes]. (b) JSONC (comments allowed) for the keymap and themes, through a hand-written comment stripper of about 40 lines with tests (a `shortcut:` comment for its limit), or a crate (a new dependency, D15). Zed's keymap is JSONC; the owner's Zed habit is the reason to ask.
- **D11 — keymap editing.** Options: (a) file only in this plan: `keymap.json` is read at start and edited by hand [recommended: RI-13 names the file, and an in-UI rebinding needs a key-capture step that the legacy encoding cannot complete for some keys]. (b) A Keymap section on the Settings page that records the next key press. Under (b) the phase needs a capture dialog and a rule for keys the terminal cannot send.
- **D12 — `Ctrl+,` and its fallback.** Facts: the legacy encoding cannot send `Ctrl+,` (`input-parser.zig:489-491`); the kitty protocol sends it (`input-parser.zig:1269`, `host.rs:147`). Options: (a) `Ctrl+,` and a plain `,` outside prompts [recommended: `,` is unbound on every page (`src/keys/parser.rs:145-254`), it mirrors RI-12's `Ctrl+. .`, and a terminal that sends the plain comma for `Ctrl+,` would then open the page too]. (b) `Ctrl+,` only: a terminal without the kitty protocol opens nothing, and the page has no other route. (c) Add `:settings` on the `:` line (`src/app/command.rs:40` `run`), which works in every terminal [recommended as an addition to (a)]. Rejected by the facts: `Cmd+,` (the macOS convention) needs the kitty protocol too, and Terminal.app may take it for its own Preferences (not checked here).
- **D13 — a hand edit made while fmc runs.** Options: (a) restart only, as every key does now (`architecture.md`, "a read-only settings.json": "a setting is read once at start"); the page's own saves apply at once and re-read the file first [recommended]. (b) The page re-reads `settings.json` each time it opens (no watcher, no polling). (c) A watcher (RI-8 is parked). Under (a) a save that finds a file it cannot parse refuses and changes nothing.
- **D14 — a symlinked `settings.json`.** Options: (a) write through the link to its target, so a dotfile link stays a link [recommended]; the target may lie outside `~/.config/fmc`, and the security review checks that. (b) Refuse with a notice. (c) Replace the link with a file (breaks a dotfile manager's setup). Recommended (a) is the only option that keeps the owner's setup intact; (b) is the strictest.
- **D15 — dependencies.** None new is needed: `serde_json` (already declared) reads and writes `serde_json::Value`, and `std::fs` covers the temp file and the rename. `serde` with `derive` is approved (`rules.md`, "Approved for after parity") but unused here. `tempfile` is a dev dependency only (`Cargo.toml` `[dev-dependencies]`); using it in production would need a new approval. Recommend: confirm no new crate. A JSONC crate under D10 (b) would need one.
- **D16 — parity records.** The three features are post-parity deviations from Scouter's "no configuration" (`scouter:docs/decision/0001-read-only-and-minimal.md:7`), fixed palettes (`scouter:src/ui/theme.ts:115-127`), and fixed keys (`scouter:src/core/keymap.ts:3-55`). Options: (a) the owner's request is the approval; each phase commit carries its `architecture.md` record and its `docs/parity.md` line, and the owner reads that text at the phase's go-ahead [recommended]. (b) The owner approves each record's wording before its phase starts.

### Decisions (dated, agent picks)

These picks are the agent's, dated 2026-11-27. Each is one line to change; the owner can overrule any of them before its phase.

- **A1 (2026-11-27): the write is atomic.** `services/settings.rs` writes a temp file in the same folder (`.settings.json.<pid>.tmp`, `create_new`), calls `sync_all`, and renames it over the target, removing the temp file on any error. Rejected: `fs::write` (it truncates before the new bytes exist, so a crash loses the file). Rejected: `tempfile::persist` (a dev dependency, D15).
- **A2 (2026-11-27): a save merges into the file as it is now.** The save re-reads the file, parses it as an object, sets only the keys the page changed, keeps every other key, and refuses when the text does not parse (the bytes stay as they were, and the page shows a notice). Rejected: writing the whole in-memory `Settings`, which drops unknown keys and hand edits made after start.
- **A3 (2026-11-27): a save sorts the keys.** A `serde_json::Map` has no file order (`Cargo.toml`, no `preserve_order`), so the first save sorts the keys alphabetically; the phase 3 record says so. Rejected: enabling `preserve_order`, a new feature on a pinned dependency, which would need the owner's approval for a cosmetic gain.
- **A4 (2026-11-27): the bundled catalog is JSON.** The bundled themes are JSON files in `src/theme/catalog/`, embedded with `include_str!`, parsed by the same function as a user file. Each set carries bjarneo's MIT `LICENSE` beside it, as the highlight queries do (`rules.md`, "Licenses").
- **A5 (2026-11-27): the palette fields become `Cow<'static, str>`.** Built-in palettes stay `const` (`Cow::Borrowed`); a user theme owns its strings (`Cow::Owned`). Rejected: `Box::leak` (a shortcut with no limit, and it hides the lifetime), and `Arc<Palette>` with `String` fields (it rewrites `DARK` and `LIGHT`, which `theme_tests.rs:55-70` pins to `DESIGN.md`). Amended by A15: the fields are `Hex`, not `Cow`; the rejections stand.
- **A6 (2026-11-27): the page draws its rows like the tree.** `ui/settings.rs` draws each row with fmc's segments, the way `ui/tree.rs` draws a row, not with OpenTUI `Select`; a row shows a value column that `Select`'s name and description do not give. A spike in phase 3 may overturn this, and the phase commit says which.
- **A7 (2026-11-27): the settings keys are these names.** `theme_mode` (`auto` | `dark` | `light`), `dark_theme`, `light_theme` (catalog ids, default `scouter`). An unknown id or mode keeps the default and shows a notice, as `find_mode` does (`src/settings.rs:99-106`). The page's row labels and the key names are the same words.
- **A8 (2026-11-27): the key table is data, and the defaults reproduce the match arms.** Phase 4 moves the bindings into `keys/bindings.rs` as a list of (context, key, action). The defaults give the same `Step` for every key in `keys/tests.rs`, unchanged. Rejected: a second parser beside the match arms, which would let the help and the dispatch drift again.
- **A9 (2026-11-27): the bjarneo roles map to fmc's values as follows.** Source values (role index, in the order `bjarneo/editor` `src/theme.rs:41-43` gives): `bg` (0) to `fallback-background`; `bg3` (2) to `row-active-bg` and `hover` ("the cursor line and hovers", `bjarneo/editor` `src/theme.rs:10-11`); `bd` (3) to `border`; `fg` (4) to `text`; `fg2` (5) to `muted`; `fg3` (6) to `dim`; `ac` (7) to `accent`; `on` (23) to `accent-ink` ("text drawn on an accent fill"); `sel` (22) to `selection-bg`; `err` (21) to `error`; `kw` (11), `fun` (12), `str` (13), `num` (14), `com` (17), `pun` (18) to the six `syntax-*` values. Candidates, not source values: `err` to `removed`, `warn` (20) to `modified` and `match-bg`, `ins` (8) to `added`, `bg` to `match-fg`. No source value (fmc derives them under D8 (b), or the file must give them under D8 (a)): `accent-soft`, `ignored`, `folder`, `added-bg`, `removed-bg`, `added-gutter`, `removed-gutter`, `target-bg`, `target-gutter`, and the three `wordmark` values. Unused by fmc: `bg2` (1), `vis` (9), `cmd` (10), `ty` (15), `mac` (16), `prop` (19).
- **A10 (2026-11-27): a user binding shows in `?`.** The card (`?` and `--help`) reads the merged table: each default row's keys change to the user's keys for its action, and a new binding gets its own row under its context. Rejected: a separate "custom keys" section, which would repeat what the table already says.
- **A11 (2026-11-27): a bad keymap entry is skipped, the rest apply.** An unknown action or context, or a key name the parser does not know, skips that entry with a notice that names the line (RI-13's rule). A `null` value unbinds the default key. A user binding that shadows a prefix (`g` in `gg`) takes effect in the parser's `More` state, which reads the merged table (RI-13's trap).
- **A13 (2026-11-27): the id `scouter` is Scouter's pair.** In a dark slot it is `DARK`, in a light slot it is `LIGHT`. A bundled or user id names one mode and is used only in its own slot; a wrong-slot id keeps that slot's `scouter` and adds a notice, and an unknown id does the same (A7).
- **A14 (2026-11-27): a forced mode that differs from the terminal uses the palette's background.** The page background is the terminal's background tinted (`tinted_background`) only when the palette's mode is the terminal's; otherwise, and when the terminal did not answer, it is the palette's `fallback-background`. `page_background` in `theme/mod.rs` holds the rule, and its test pins both cases.
- **A15 (2026-11-27): the palette fields are `Hex`, not `Cow`.** `theme::Hex` is seven bytes (`#rrggbb`, lowercase), `Copy`, with a `const fn` constructor for the built-in consts (`Hex::new`), a fallible `Hex::parse` for files, `Deref<Target = str>`, and an RGB constructor for derived values. `Seg.fg` and `Seg.bg` are `Option<Hex>`. Reason: `Seg` colours are read about 280 times as `Some(p.x)` or by value, and `Cow` would need a clone at each read; `Copy` keeps them. This amends A5.
- **A16 (2026-11-27): the bundled themes that fall short are listed, not hidden.** The contrast thresholds of `theme_tests.rs` stay as they are. Found when the catalog was added: twelve bundled themes fall short of 7:1 on a tint (`text/added-bg`, `text/removed-bg`, `text/target-bg`, `text/row-active-bg`, `text/selection-bg`) or on `match-fg/match-bg`, and tokyo-night-day also falls below 4.5:1 on three of its tints (`text/added-bg` 4.36:1, `text/removed-bg` 4.11:1, `text/target-bg` 4.02:1; the lowest is 3.85:1 on `text/selection-bg`). `SHORT` in `theme_tests.rs` lists each pair, and the test fails on a new shortfall or on a listed pair that passes. The owner decides: keep the colours and the list, change a colour, or change a threshold.
- **A17 (2026-11-27): a theme file's id is its file name, and `parse` takes it.** `catalog::parse(id, text)` takes the id, so the name defaults to it; the phase text's `parse(text, base)` took no id and no base, since the derived values come from the roles (D8 b). A file named `scouter.json` is refused with a notice, because `scouter` is built in.
- **A18 (2026-11-27): the footer shows the notices in their order.** The settings file's notices come first, then the theme files', then the palette choice's (`app/mod.rs` `run`), joined on one line as the settings notices were. A long line is cut at the footer's width, as any footer text is.
- **A19 (2026-11-27): Left and Right step a choice back and forward.** Enter and Space step forward, as the plan's keys say. Left (and `h`) step back and Right (and `l`) step forward, because a choice with no way back would be a one-way walk through the theme ids. Rejected: a Shift or Backspace binding, which a terminal may not send.
- **A20 (2026-11-27): one save is in flight at a time.** A change made while a write runs waits in a queue, and the next write takes the queue as one batch (`app/settings.rs` `start`). A refused batch takes back itself and the queue, last first. Rejected: refusing a change while a save runs (a held key would be refused), and one write per change in parallel (two writes would race on the file, and the second would lose the first's key).
- **A21 (2026-11-27): the page is modal to the mouse.** While the page is open the dialog's catcher covers the screen (`app/overlay.rs` `draw`), so a click or a wheel step on the list or the reader does nothing, as it does under a dialog. The rows take keys only. Open for the owner: whether a click should select a row, which the plan does not name.
- **A12 (2026-11-27): a live run uses a temporary config folder.** Every live run sets `XDG_CONFIG_HOME` to a temp folder (`src/services/settings.rs:12-18` reads it), so the owner's `~/.config/fmc` is never touched by a test.

### Execution rules

- **One atomic commit per phase**, with the message the phase names. A phase's commit carries the docs for its own behaviour (`rules.md`, "Where a fact lives"). The index and the roadmap move in phase 5 only.
- **Execution waits for the owner's explicit "continue with phase N".** The owner's answers to D1 to D16 are needed before phase 1 starts; D1 must be answered before phase 1, since phase 1 changes the write rule. After the last phase, the agent recommends the closing commit and its paths; it does not commit the closing state on its own.
- **Branch:** `docs/plan-00015-settings` for this drafting; each phase's code work runs on `feat/plan-00015-settings` (or the branch the owner names), never on `main`. Nothing is pushed.
- **No new dependency** unless D15 or D10 (b) says so. `cargo deny check licenses` stays green; the bundled catalog's MIT notice is a file in the tree, not a crate.
- **Gates before each commit:** `KACHE=false just verify` green (`docs/development.md`), then `cargo build`. Rust code follows `rust.md`; a phase that changes what is drawn or how a key is handled also gets a live run.
- **Writes are tested in temporary folders only.** Tests set `XDG_CONFIG_HOME` to a temp folder (A12); no test reads or writes the owner's `~/.config/fmc`.
- **Sample data** comes from Dan Brown and Harry Potter (`rules.md`, "Sample data"), in fixture names such as `gringotts.rs.bak` and `hogwarts-settings.json`.
- **The owner's parallel work is untouchable:** the untracked `.claude/worktrees/` is not part of this plan.
- **A phase's undo is named before the phase starts.** Phases 1, 2, and 3 are `git revert` of their commit (no user file is changed by a revert, because a write only happens from the page, phase 3). Phase 4 is the riskiest: it replaces the `match` arms in `src/keys/parser.rs` with a table, so its undo is `git revert` of its commit, which restores the arms. Every `keys/tests.rs` test must pass unchanged in phase 4 before its commit, and a red test stops the phase.
- **Live runs** (`run` skill, or Rex under `rex` in a new tab of the agent's own session, with `rex run -s "$REX_BLOCK" --focus=false -- …`): the page, the theme, and the card at 80x24 and 120x40. The owner's panes are not typed into (`AGENTS.md`, "Rex live runs").
