# Mermaid engine spike for plan-00006

Point-in-time research, 2026-11-27. Plan: `.agents/docs/plans/plan-00006-mermaid-grammars-fuzzy.md` phase 1 (decision O1: spike both engines, then the owner picks). Agent audience; evidence as `file:line`. The spike project is `/tmp/fmc-spike/mermaid` (outside the repository; it holds the copied Grok code, which is not kept here). Nothing in fmc's `Cargo.toml`, `Cargo.lock`, or `src/` changed. Local toolchain: rustc and cargo 1.100.0 (2026-11-09), macOS arm64. Grok source read from `/tmp/fmc-ref/grok/src` (read only; no cargo run there).

## 1. Recommendation

Pick **mermaid-text 0.58.0 with `RenderOptions::max_width_strict = true`** (Engine B), unless the owner rejects its MSRV of 1.92.

Reasons:

- **Fit.** D2 says a diagram wider than the reader falls back to the framed source. The Grok engine never compacts: it lays out once at the natural width and falls back when the canvas is wider (`xai-grok-markdown/src/mermaid.rs:1987-1990`, original file). The Harry Potter flowchart is 104 columns natural, so it is framed at both 60 and 100 columns. mermaid-text compacts through gap configurations (`mermaid-text/src/lib.rs:283`, doc of `render_with_width`), and its strict mode turns the budget into a hard check that returns `TooWide` (`lib.rs:180-185`, `539-560`). The flowchart is 98 columns at 100 and 70 at 60 (it overflows 60 with the soft hint, so strict mode frames it at 60).
- **Coverage.** mermaid-text has 18 diagram kinds (`src/detect.rs`, `DiagramKind`), including gantt, which is the owner's sample set. Grok has 5 (flowchart with subgraphs, state, class, ER, sequence, `mermaid.rs:58-89`); gantt, pie, and the rest fall back to the frame.
- **Reasons.** mermaid-text returns typed errors (`UnsupportedDiagram("this")`, `ParseError`), which give the one-line fallback reason plan phase 2 needs (`unsupported diagram: gantt`, `parse error at line 3`). Grok's fallback has no reason text.
- **Code to keep.** mermaid-text is a dependency. Grok is 3,968 non-test lines of forked code plus Apache-2.0 attribution, which fmc would own and re-port by hand.

Costs the owner must accept:

- **MSRV 1.92.** fmc's floor is 1.90 (`Cargo.toml:9`). mermaid-text and `ascii-dag` declare `rust-version = "1.92"`. The pinned toolchain (1.100) builds it.
- **Six new crates** on macOS arm64: `ascii-dag`, `chrono`, `iana-time-zone`, `core-foundation-sys`, `num-traits`, `unicode-width`. All MIT or MIT OR Apache-2.0, all on the `rules.md` allowlist. None is in fmc's `Cargo.lock` today (checked by grep).
- **Output quality is not finished.** mermaid-text reorders class members (`+String passcode` renders as `+passcode String`), crowds edge labels against a diamond node, and the sequence layout ignores the width hint (70 columns at 60, so strict mode frames it). It also accepts some malformed flowchart text as a node label without an error (`broken.mmd`, section 4). Phase 2 should either test these or accept them.

If the owner rejects the MSRV bump, Engine A is the only option without it. Its cost is the fallback for most flowcharts at phone widths, and no gantt. That is a trade the owner should see before choosing it.

## 2. Engine A: the Grok port

Source: `crates/codegen/xai-grok-markdown/src/mermaid.rs` (5,699 lines in the Grok repo at `/tmp/fmc-ref/grok/src`). License `Apache-2.0` (`crates/codegen/xai-grok-markdown/Cargo.toml`, `license`); the repo `LICENSE` reads `Copyright 2023-2026 SpaceXAI`. Its external imports are Ratatui and `unicode-width` (`mermaid.rs:8-10`).

Diagram dispatch (original file, `render`): flowchart or graph with subgraph groups (`render_grouped`), then state, class, ER, and sequence; anything else is the framed source (`mermaid.rs:58-89`). Gantt, pie, and the others are not parsed.

What changed to make it plain text (spike copy, `/tmp/fmc-spike/mermaid/src/grok/mermaid.rs`, generated by `/tmp/fmc-spike/port_grok.py`):

- Removed the Ratatui imports and `MermaidStyles`; `MermaidArt` became `Vec<String>`. `to_lines` returns the plain rows only; `style_for` is gone.
- Removed the `styles` parameter from the six functions that took it, and its call sites.
- The framed fallback builds plain rows only. The italic hint line lost its modifier.
- Tests: the `styles()` helper and one test that compared styled and plain widths were removed; the other 144 tests call `render(src, width)` and check the plain rows. All 144 pass (`cargo test` in the spike).
- Diff against the Grok file: 157 lines removed, 42 added (6 of them the attribution header). Non-test lines went from 4,052 to 3,968; test lines from 1,647 to 1,616.
- Left in place: the canvas's per-cell style class (`Cls`, about 45 references). It no longer affects output and could be removed in a follow-up, which I did not measure.
- Fmc-specific change needed before use: the fallback hint reads "open the image to view it in full" (`mermaid.rs:3922-3923`, original). fmc has no image view for a diagram, so phase 2 replaces that text.

Dependency: `unicode-width` 0.2.3 (MIT OR Apache-2.0, `rust-version` 1.66 in its metadata). Not in fmc's `Cargo.lock` (checked with grep). No other crate: the closure of `unicode-width` is itself.

## 3. Engine B: mermaid-text 0.58.0

MIT (`Cargo.toml` `license`), `rust-version = "1.92"`. Used through `render_with_width(input, Some(width))` (`src/lib.rs:283`), and for the strict check through `render_with_options` with `RenderOptions { max_width, max_width_strict: true, .. }` (`src/lib.rs:539-616`). The width is a soft hint by default: sequence, pie, and ER have fixed layouts and ignore it (`lib.rs` `RenderOptions::max_width` doc, around line 543). `Error` has four variants (`lib.rs:167-185`): `EmptyInput`, `UnsupportedDiagram(String)`, `ParseError(String)`, `TooWide { requested, actual }`.

Diagram kinds (`src/detect.rs`, `DiagramKind`): Flowchart, Sequence, State, Pie, Er, Class, Journey, Gantt, Timeline, GitGraph, Mindmap, QuadrantChart, RequirementDiagram, Sankey, XyChart, BlockDiagram, Architecture, Packet (18).

## 8. The width question

`CodeBlock` carries no width. Its fields are `app`, `language`, `info`, `code`, `closed`, `conceal`, `streaming`, and `previous` (`opentui-0.9.9/src/widget/markdown.rs:157-174`). The renderer type is `Fn(&CodeBlock) -> Option<AnyWidget>` (`markdown.rs:631-645`, `code_block_renderer`). A renderer therefore cannot read the reader's width from its arguments.

Invocation sites (`markdown.rs`):

- `build_block` calls `code_block` for each new block (`998`, `1013`).
- `update_code` runs it again when a code block's text changes (`928-931`).
- `rerun_renderers` runs at the end of streaming (`1359-1375`).
- `rebuild_where` (`1394`) rebuilds the subtree (`rebuild_subtree`, `1403-1426`) on `restyle` (`1385-1391`), when a renderer is registered or removed (`642`, `650`), and on the options that change prose (`557`, `666`).

Resize: none of these is a resize path. `markdown.rs` has no width-driven hook, so a window resize does not call the renderer again. fmc's own resize handler calls `paint`, which sets the reader and preview widths (`app/mod.rs:305-311`, `687-688`), not the Markdown view. `MarkdownView::show` is `set_markdown` (`src/ui/markdown.rs:49-51`), called from `src/app/reader.rs:122` on open.

The route that gets the width at layout time is a measured custom widget:

- `Custom::measured(app, component)` makes a widget sized by `Component::measure(width: Constraint, height: Constraint) -> (f32, f32)` when its width or height is not set (`opentui-0.9.9/src/widget/custom.rs:155-171`; trait method `custom.rs:63`). It cannot have children.
- `Measure::measure` runs inside native layout; its doc says it "reports a leaf node's size during layout" (`src/native/measure.rs:41-42`). `Constraint` is `Unbounded`, `Exactly(f32)`, or `AtMost(f32)` (`measure.rs:11-18`), so the offered width arrives as a value.
- `Custom::update` marks the node dirty and requests a redraw (`custom.rs:190-196`), so a change re-measures.
- Painting uses the box's own width, `Painter::width()` (`widget/painter.rs:43`).
- The renderer returns the widget as an `AnyWidget` with `Widget::as_any` (`widget/mod.rs:778`).

Plan for phase 2: the renderer returns a measured `Custom` whose component keeps a cache keyed by (source, width). `measure` computes the rows for the offered width and returns (width, rows); `paint` draws the cached rows. `measure` takes `&self`, so the cache sits in a `RefCell` inside the component, and `measure` must not change other widgets (`custom.rs` `Component::measure` doc).

Open point: whether native layout calls `measure` again on a width-only change. That logic is in the native library (zig), not in the crate source, so I could not read it. Phase 2 has to prove it with a live run at 60 and 100 columns and a resize. If it does not re-measure, the fallback is fmc's resize handler (`app/mod.rs:305`) setting a shared width cell and calling `MarkdownView::show` again, which rebuilds the document.
