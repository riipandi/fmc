# Rust

updated: 2026-11-28T23:00:00+07:00

Rust contracts and traps for the `fmc` crate. Gates and commands: `shape.md`. Cross-area rules, including parity with Scouter: `rules.md`.

## Toolchain facts

- Edition 2024 (`Cargo.toml:3`). Rules for new or changed code:
  - Every unsafe operation sits in an explicit `unsafe {}` block, even inside an `unsafe fn`; `extern` blocks are `unsafe extern`.
  - `gen` is a reserved keyword.
  - Tail-expression temporaries and `if let` scrutinee drop order changed in 2024: check them when a lock guard or a borrow is involved.
- The engine is `opentui` and `opentui-sys` =0.9.9 with the `tree-sitter` feature (`Cargo.toml`). Read the API from the locked source; docs.rs for the locked version is the second source.
- `rust-version = "1.92"`: the floor set by `mermaid-text` 0.58.0 (owner decision O4, plan-00006; it was 1.90 for `tree-sitter` 0.27.2). The pinned toolchain (`rust-toolchain.toml`, 1.100.0) builds it. No 1.92 toolchain is installed here, so `cargo +1.92 check` has not run.

## Layout rules

The layout and its reasoning: `architecture.md` ("a pure core, I/O services, and the UI"). These rules bind once `plan-00001` phase 5 creates the modules.

- The core (`src/lib.rs` and its modules: `keys/`, `explorer/`, `reader/`, `find/`, `diff/`, `overlay.rs`, `theme/`) has no I/O and does not import `opentui`. It takes values and returns values.
- A keymap returns `Action`s; `src/app/` carries them out.
- No file I/O and no process spawn on the UI thread. Workers in `src/services/` do it and send `Event`s back.
- Keep every file under 800 lines.
- Tests go in a sibling `tests.rs` or `*_tests.rs` file, not in an inline `mod tests` block of a large file.
- The `tree_sitter` crate is not a direct dependency: it is reached through `opentui::syntax::tree_sitter` (`opentui-0.9.9/src/syntax/highlight.rs:17`). Code that parses Markdown source with it (`ui/markdown_blocks.rs`) therefore sits in `ui/`, not in the core. `Node::kind()` borrows from the tree; copy it to a `String`.

## Code rules

- No `.unwrap()` or `.expect()` in non-test code unless the panic is a true invariant, marked `// INVARIANT: ...`.
- `unsafe` only with a `// SAFETY: ...` comment; list each one in the change summary.
- A comment carries a why, a contract, or a trap; never the next line. It never cites a plan, a roadmap entry, a decision ID, or a doc file; it says the reason in its own words (`AGENTS.md`, "Working rules").

## Contracts and traps

- **A prompt's word edits are OpenTUI's native word rule, and its caret is a byte offset.** `line_edit.rs` `Line` keeps the caret on a character boundary. `prev_word` and `next_word` follow `packages/native/src/edit-buffer.zig` `getPrevWordBoundary` and `getNextWordBoundary` at the locked 0.9.9 tag (its `utf8.zig` breaks, not in the crate: the crate binds only the native query, `opentui-0.9.9/src/widget/editor.rs` `goto_word`). `line_edit_tests.rs` holds the native test's cases. A prompt takes its edit keys before the global Ctrl bindings (`app/capture.rs` `prompt_takes`), so a Ctrl or Option key that `edit_of` names is never a command while a prompt is open.
- **File operations never reach the Trash in a test.** `app/write.rs` calls `services::write::trash` in the binary and a test function in its tests, which removes the entry through `trash_with`, so the root and name checks still run and the owner's Trash is untouched. A new write test uses the same stand-in.
- **A write is a name in a folder, never a path.** `services::write::create_dir` takes the name without a trailing `/`: the dialog strips one (`app/write.rs`), and a name that still holds a `/` is refused. Names are `&str`; a name that is not UTF-8 or holds a control character is refused before a field can show it.
- **Terminal restore is OpenTUI's.** `App::run` enters the alternate screen and leaves it on return; the host installs a panic hook that restores the terminal before the panic message prints (`opentui-0.9.9/src/host.rs`, `install_panic_hook`). fmc adds no hook of its own. `tests/cli.rs` checks both paths; the panic path uses the debug-only `FMC_PANIC_AFTER_START` variable (`src/app/mod.rs`), compiled out of release builds.
- **The root keeps the terminal's background.** OpenTUI's themes fill the root with a color (`#12161c` dark); Scouter draws on the default background, so `app::run` sets both themes' `background` to `Color::DEFAULT_BACKGROUND`.
- **A paste is one worker job, and its answer is an event.** `app/write.rs` `paste` runs `services::write::paste` through `services::spawn` and sets `Model.pasting`; a second paste is refused until `Event::Pasted` answers, and `pasted` clears the flag before it reveals or refuses. The footer's status is set before the job starts, and the 2 s timer (`app/mod.rs` `clear_message_later`) leaves it alone while `pasting`. The clipboard is fmc's own: a copy stays until Esc; a cut ends with its paste. A duplicate is the same job with `moved` false (`app/write.rs` `duplicate`): it checks the name on the UI thread with `services::write::check_copy`, so a taken name keeps its dialog open, and the answer reveals the copy through `pasted`.
- **A write checks identity around each step a swapped entry could reach.** `services/write.rs` `copy_then_remove` records the source's `(dev, ino)` before the copy and refuses the removal when it changed (`Error::Changed`). `open_seen` opens a file and compares the opened file's `(dev, ino)` with the `lstat` taken before, so a link swapped in is refused before a byte is read; `File::open` follows links, so this comparison is the guard. A folder copy checks its identity the same way before it creates the destination (`copy_seen`, tested with a folder swapped for a link after its `lstat`). The `read_dir` after that check follows a link too, so a swap in the gap still copies the outside folder (`shortcut:` in `copy_seen`).
- **The dialog's field holds the keyboard only while the dialog's focus is on it.** `app/overlay.rs` `draw` focuses the field when `Dialog.focus` is `Stop::Field` and blurs it when the field still holds the focus otherwise, so the terminal cursor shows in the field alone. fmc focuses nothing else, so the blur is limited to the field. A pointer over a menu row selects it (`app/overlay.rs` `hover`); a pointer over a dialog button only highlights it (`hover_button`, `Dialog.hovered`), and the focus stays where the keys put it, so Return picks the focused button. The menu's motion needs OpenTUI's motion tracking, which `AppOptions::default()` sets (`MouseTracking::Motion`); a button's enter and leave come from `on_hover`.
- **A dialog's field edits come from fmc's table, and OpenTUI's keymap only names their actions.** The overlay takes every key in capture, so `Input::default_keymap` never runs for the field. `overlay.rs` `field_edit` names the keys (Option is `alt`, Cmd is `Key.cmd`, which `plain()` ignores), and `app/overlay.rs` `editor_action` runs each edit as the `EditorAction` the default keymap binds to the same key; `app/overlay_tests.rs` checks those bindings against the keymap. A key the table leaves out is swallowed by the dialog.
- **A key is bound in one row of `keys/bindings.rs` `DEFAULTS`, and the merged keymap is the only dispatch source.** `Parser` walks `Keymap::bindings()`: the user's rows (`keys/keymap.rs`) come first, then the defaults they did not replace or unbind. The pending sequence reads the same rows (`Parser::lookup`): a row that continues the pending keys wins, so a lone `g` waits when a user binds `g x`, and a key that cannot continue the sequence cancels the wait and is read alone. Count digits and `z` stay in code, not rows. A row's modifiers match where the old `match` arms checked them: `ctrl-` and `alt-` ignore Shift, `*-` ignores all modifiers (Tab, Escape), named keys and symbols ignore Shift unless a `shift-` row comes first, and `.` checks Shift. `keys/tests.rs` pins the defaults and must pass unchanged; `keys/keymap_tests.rs` pins the file.
- **An `Action` name is public.** `Action::name` and `from_name` read `ACTION_NAMES` in `keys/bindings.rs`; a parameterized action has one name per value its rows use (`move_down`, `move_down_five`). A rename breaks users' `keymap.json` files, so a rename needs a deliberate decision, not a drive-by edit. `GoToLine` has no name: a count is not a key.
- **The card and `--help` read the merged keymap, not the defaults.** `key_sections(keymap)` (`keys/mod.rs`) gives a `ROW_ACTIONS` row its keys from the merged table, and its fixed label while those keys are the defaults; a binding of an action with no row gets a row of its own. `key_page_markdown()` and `key_list_text()` (no argument) are the defaults, for tests and the help text without a file.
- **The remembered state is written from a paint, so a new remembered value joins `remember::snapshot`.** `app/remember.rs` `snapshot` names every value `fmc::state` keeps, and `sync` compares it at each paint. A toggle needs no write of its own, but a change that does not reach a paint is not written until the next one, and a value missing from `snapshot` is never written.
- **The rendered source is prepared the same way at every site.** The view reads a Markdown source as `frontmatter::as_fence` (the front matter as a fence, the same line count), then `headings::with_markers`, and the block split reads the fenced text too. `ui/markdown.rs` `show` and `block_lines` and `ui/markdown_search.rs` `index` each do it; a new site that reads the rendered source must do the same, or its block numbers and search rows drift from what is drawn.
- **Keys are read in capture.** `on_key_capture` (`app/capture.rs`) sees every key before widgets, as Scouter's `keyInput` handler does; `tab_focus` is off so OpenTUI does not move focus on Tab. A key the parser hands to fmc calls `stop_propagation`: OpenTUI's keyboard focus follows the last click, not fmc's `Focus`, so the reader's scroll box would otherwise pan on a tree arrow (`app/capture_tests.rs`).
- **The settings file is read before the UI starts, and written only by the Settings page's worker.** `main.rs` calls `services::settings::load` before `app::run`, and `app::run` shows the notices once in the footer. The schema file is the other start-time write: `main.rs` calls `services::settings::ensure_schema` after the terminal check, and its notice joins the settings notices. The core's `settings::parse` takes the text and touches no disk. The one write, `services::save_atomic` (`services/mod.rs`), takes the text `settings::merged` returns, and writes it through a temp file and a rename, so a reader never sees half a file (`architecture.md`, "fmc writes its settings.json, atomically"); `services::settings::update` reads the file again and makes that text. A value reaches the app only when the feature it sets is built (`app/mod.rs`).
- **The schema is built from the rows and name lists the parser uses.** `settings::schema()` (`src/settings.rs`) takes its keys from `Row::ALL` and `file_associations`, its defaults from `Settings::default()`, and its names from `Matching::ALL`, `ModeChoice::ALL`, `Language::names()`, and `slot_ids`. `parse` reads every key through `field`, which `debug_assert`s the key is in `settings::KEYS`; `settings_tests.rs` checks `KEYS` against `schema()`'s properties and against `parse`'s notices, so a key added to `parse` fails the tests until it is in `KEYS` and has a schema property. `merged` adds `$schema` to a file that has none (`SCHEMA_LINK`), `linked` inserts it as the first key at start without touching the other bytes, and `parse` ignores that key without a notice.
- **A settings save is one worker job at a time, and a refusal takes its changes back.** `app/settings.rs` `commit` applies a change at once and queues it with the settings before it; `start` sends the queue to `services::spawn` as one batch while none is in flight, and the answer `Event::SettingsSaved` reaches `app/settings.rs` `saved` through `settings::event`. A refusal reverts every change of the batch and the queue, last first (`Settings::take`, then `apply`), so each row returns to its value before them. `apply` returns whether the colours changed, and only `restyle` (which needs `&mut Ui`) repaints them: a path that holds only `&Ui`, the number dialog's OK in `write.rs` `submit`, may change a number row, which changes no colour. The page takes every key and click while it is open (`app/capture.rs`, `app/overlay.rs` `draw`).
- **A preview is a timer, a generation, and its own event.** `app/preview.rs` `moved` counts each list move and starts a 100 ms timer; the timer reads the selected file only if it is still the newest move (`due`). The read comes back as `Event::Selected`, which the tree applies only while the same file is selected, so a late read never replaces a newer selection, and it never moves the focus or pushes a jump.
- **A poll is one job per chain, and its answer schedules the next.** `app/poll.rs` starts one worker job per tick, and the back-off is three times the job's duration, within 2 s and 30 s (`src/explorer/browse-watcher.ts`). A browse refresh that is not a tick (leaving the changes screen) sets `chain` false, so it cannot start a second chain; a changes tick ends when its session has left the screen.
- **A rebuilt stacked body holds its end after the frame measures it.** A rebuild that found the body at its end sets `bottom_pending`, and the repaint 20 ms later scrolls to the new end once the blocks have rows (`app/mod.rs`). A scroll before that moves the selection to the last file, because the block tops are not laid out yet.
- **The sign strip's column is a blank sign on line 1.** `LineNumbers` sizes its gutter from the signs it holds, so with none the gutter is one column narrower and the numbers move when the first sign appears. `ui/reader.rs` `draw_signs` draws a blank sign on line 1 while the strip is on, and a real sign on line 1 replaces it.
- **Signs ride the browse tick, and an answer needs its showing.** `app/poll.rs` `browse_now` asks for the shown text's signs as a job of its own (`app/gutter.rs` `request`), so the poll's back-off is unchanged. `apply` keeps an answer only for the `Shown::Text` with the same path and `serial`; a git error clears the signs with no notice.
- **Workers answer through events.** `services::spawn` runs a job on its own thread and sends the `services::Event` it returns through the app's `AppProxy`; `app/` applies each event on the UI thread. A reply may arrive after the tree changed, so `apply` checks that the path is still in the tree.
- **Git runs on a private index copy, one per repository.** `services/git.rs` `Repository` copies `.git/index` before a listing, keeps the copy's mtime (git's racy-index check), and copies again unless the index and the copy are unchanged and the index is older than 2 s (`src/diff/git.ts:156-198`). `Drop` removes the copy. Git's `diff` rewrites the index it reads even with `GIT_OPTIONAL_LOCKS=0` (Scouter decision 0007). A patch diffs against the base of the last listing and reads the copy that listing made, so call `changes()` before `patch` or `patches`.
- **Each git call is bounded and queued.** A call is killed after 15 s (it then reports `git exited with status 143.`, as Scouter's Bun timeout does), and a listing past 8 MiB has no text. A patch is cut at 1 MiB, the stacked diff at 4 MiB, and the files past the cut are not shown. One queue per repository runs one call at a time. A quit during a call leaves its copy in the temp directory until `main.rs` (`RemoveCopies`) calls `services::git::remove_copies`, which removes every copy still registered, as Scouter's exit hook does (`src/diff/git.ts:372-375`); a copy is registered from its creation to its `Drop`.
- **A conflicted file lists as modified.** `git diff <base> --name-status` reports it as `M`, so the `U` letter (`Conflict`) never comes from the change list; the `Unmerged:` notice is unreachable there, as in Scouter (`research/scouter-inventory.md` §21).
- **A text search stops, and a preview answers its latest request.** Each text search runs on a worker that checks an `AtomicBool` between files and reports progress every 120 ms (`services/find.rs`). A new query stops the running search and bumps the `Generation` (`find/text.rs`); an event for an older number is dropped. A preview read answers the latest request, and an older answer is dropped (`app/find.rs`).
- **The finder shows its matches in the tree's list.** `Browser::show` replaces the tree's rows with flat rows and `show_tree` brings the tree back (`explorer/browser.rs`); `row_count` is what the list and its scrollbar measure, and an empty list is valid. `Browser::rows` borrows the whole browser, so a method that also sets `selected` copies the new path out before it assigns.
- **A bar's drag is a transparent slider over its column.** `ui/scrollbar.rs` `track` lays the crate's `Slider` over the last column of each bar (the thumb's; a press on the blank columns before it does nothing, as in Scouter), so the press, drag, and track click are OpenTUI's (Scouter's bars are sliders too); `sync` sets its range, thumb, and value from each frame, and `track` drops a release, which the slider would apply again to the drawn thumb's offset and move by up to a row. The track sits above the thumb's cells (`z_index`), or a press on a cell misses it.
- **The tree is drawn from a scroll position.** `ui/tree.rs` paints only the visible rows; the scrollbar column exists only while the list overflows (a hidden widget takes no space).
- **Overlapping captures cascade as Core's.** The vendored grammars register with `Grammar::core_captures()` (`src/ui/syntax/mod.rs`, `grammar`). Without it, a TOML key takes `(bare_key) @type`'s style where Scouter shows `(pair ...) @property`'s; with it, every vendored grammar's captures match Scouter's (plan-00001 phase 11). Rust, bundled with `opentui`, is registered by the binding and matched Scouter without it.
- **Core's queries use `#match?`, not `#lua-match?`.** The binding evaluates tree-sitter's regex predicates and ignores unknown ones, so a `#lua-match?` would colour every identifier. `src/ui/syntax/queries/{typescript,typescriptreact,zig}/highlights.scm` carry the translation (same patterns; the comment pattern takes `(?s)`); the test `typescript_names_a_property_as_core_does` pins one capture.
- **The Markdown injections are the binding's own.** `src/ui/syntax/queries/markdown/injections.scm` is the text of `MARKDOWN_INJECTIONS` (`opentui-0.9.9/src/syntax/highlight.rs`), not Core's: Core's `#set-lang-from-info-string!` and `#offset!` are not evaluated, and inline text needs `injection.include-unnamed-children` to keep its backticks in the string colour.
- **The finder's fuzzy positions are byte offsets.** `neo_frizbee` reports the bytes of each matched character, and a character of several bytes is reported by all of them. `find/mod.rs` `char_positions` turns them into character positions, which `ui/tree.rs` `marked_text` draws (the test `fuzzy_positions_are_the_character_positions_of_the_match` pins it).
- **A filetype comes from one lookup with the model's associations.** `ui/syntax/mod.rs` `language_for(associations, opened, path)` is the only filetype lookup. An association comes first; then `reader/language.rs` `extension_filetype` (the extensions OpenTUI's table lacks, `.tf` and `.heex` among them); then OpenTUI's `filetype_for_path`, kept only when `HIGHLIGHTED` lists it. The reader (`app/reader.rs`), the finder's preview (`app/find.rs`), and the changes screen (`app/changes.rs` `sync`, which joins the repository root to the change's path) pass `Model.associations` and `Model.opened` (the folder fmc opened). `is_markdown` reads its result, so an association also decides `m` (`architecture.md`, "Approved deviation: `file_associations`").
- **A heading's marker is written into the source, as entities.** `reader/headings.rs` `with_markers` runs in `MarkdownView::show` before `set_markdown`: each ATX or setext heading keeps its real run (concealed) and gets the run again as `&#35;` entities, which take the heading's colour (a backslash escape takes the string colour). The inline hook cannot do it: its `source` has no run and levels 2 to 6 share one style. Every line stays a line, so the source line numbers hold; fenced, indented, and HTML blocks are left alone. Known limits: a multi-line setext heading and a setext heading in a list or quote keep no marker (`architecture.md`, "Decision: heading markers are a source rewrite, not an inline hook").
- **A Mermaid diagram learns its width from layout, not from the renderer.** `ui/markdown.rs` registers a `mermaid` code-block renderer, which runs when a block is built or changes, never on a resize, and `CodeBlock` carries no width. It returns `Custom::measured` (`ui/mermaid.rs`), so layout offers it the reader's width through `Component::measure`, and a resize measures it again. `measure` runs inside native layout: it must not change other widgets. The widget keeps the rows of its last measure; paint draws them when they fit the box and renders again only when they do not, because the engine is not idempotent at its own width (the gantt sample draws at 96 columns within 100 and falls back at 96).
- **Rendered Markdown has rows only after a frame.** The viewer's scrollbar and the footer's position count the widget's own height (`MarkdownView::rows`, `src/ui/markdown.rs`), which is empty until the frame lays the document out; `repaint_after_layout` (`src/app/mod.rs`) paints again 20 ms after each event and resize. `Markdown::block_rows` are screen rows that move up as the view scrolls, so their last end is not the total (plan-00001 phase 23c, audit-00001 F-03). The body and the stack clip with `Overflow::Hidden`, or a rendered block paints over the footer.
- **The reader scrolls in a `ScrollBox`, and unwrapped text is pane-wide.** `ui/viewer.rs` wraps the text, the rendered view, and the picture. Unwrapped text takes the pane's inner width with the bar's column (`app/mod.rs` paint, `set_width`), which gives Scouter's pan range (issue-00008, plan-00001 phase 23e). The wrapped row count, which the bar and the footer use, comes from a second `TextView` on the code's buffer (`CodeView::rows`), because `Code` keeps its own view private. Unwrapped text keeps its numbers in a gutter beside the box (`ui/viewer.rs` gutter slot, `ui/reader.rs` `CodeView::follow` moves it up with the scroll), so a pan moves only the text; a wheel over that gutter scrolls the box (`app/mouse.rs` `wire_gutter`).
- **Search marks name a style the buffer's table must hold.** A layer's group set names `opentui.<name>`, resolved against the buffer's style table, and the binding registers only the capture names a grammar uses. The code view installs its own table (`ui/syntax/mod.rs` `table`) with every capture name of the queries plus `opentui.search.match`; a new capture name in a query must join `CAPTURE_NAMES`, or it is drawn plain. `every_capture_of_the_owners_queries_has_a_table_entry` (`ui/syntax/tests.rs`) checks the owner's twelve queries; a name starting with `_` is a predicate's helper (`#eq? @_scope`) and is never drawn.
- **A footer tap presses the hint's key, from the last paint's cells.** `Footer::hint_cells` (`ui/footer.rs`) records where each hint sits, and `Footer::key_at` names the key under a press. A tap sends `keys::hint_presses` through `capture::press_key`, the keyboard's own path, so it runs the same Action (plan-00004, D2). The taps are a phone rule: at 80 columns and wider `app/mouse.rs` ignores them.
- **The sidebar's visibility is one rule in the medium and wide tiers.** `fmc::layout::Visibility` decides whether the sidebar shows: a document under 80 columns hides it, the welcome screen and an open finder hold it, and a crossing or a document opening or closing clears a manual choice (plan-00002, D1, D2, D7). In compact the list is a page, not a sidebar: `app/layout.rs` `shown` asks the top page of the stack (below).
- **The compact page stack draws the screen.** `fmc::layout::Pages` holds the open pages, bottom first (`Files` is never removed; `Reader`, `Changes`, `Keys`, `Find`). `app/pages.rs` `sync` runs at each paint (`app/mod.rs` `paint`, through `app/layout.rs` `sync`): Find, Changes, and Keys follow their screens, and Reader follows the focus in the reader on a document or on the changes body. In compact the top page sets the focus (Reader and Keys take it, the list pages leave it with the list) and draws: the list pages fill the screen in the browser panel, Reader and Keys in the viewer. `app/pages.rs` `back` closes the top page as its own key does, and `q` and `Esc` call it in compact (plan-00005, D2). Compact has the medium tier's panel border and two-row headers, and the list starts on row 3 like every tier (`ui/tree.rs` `LIST_TOP`; plan-00007, D1 and D2). Auto-preview does not run in compact (`app/preview.rs` `due`).
- **The medium tier's chevrons are the header's lead text.** `app/layout.rs` `list_chevron` (`‹`, on the list header while the list shows and can hide) and `reader_chevron` (`›`, on the reader header while the list is hidden) fill the header's lead cell; both headers share one press handler (`layout::wire`), which runs Back in compact and toggles the list in medium. The title is a second target for the same press (`PaneHeader::on_title_press`, `header_press`): in compact the lead and the title both go Back (plan-00007, D3). The marks `«` and `»` are drawn only at 80 columns and wider (`app/layout.rs` `lay_out`), and the header-row tap is gone (plan-00005, phase 4). `‹` and `›` measure one cell (`app/layout_tests.rs`).
- **The layout tier is one function of the width.** `fmc::layout::tier` returns `Compact` below 60 columns, `Medium` from 60 to 79, and `Wide` from 80 (`layout.rs`, `layout_tests.rs`). Every caller asks it; a raw width comparison in `app/` or `ui/` is a defect (plan-00005, D1). `BREAKPOINT` (80) is the wide edge and `COMPACT` (60) the compact edge. The tier tests run at 39, 59, 60, 79, and 80 columns. The compact tier has no welcome screen, so the welcome's narrow wrap is gone (plan-00005, phase 2).
- **A click completes on its release.** `app/mouse.rs` `Click` reports a release that ends a press at the same cell with no drag between. A header folds on it, and so does a list row (tree, finder, changes); a drag or swipe does nothing. Below 80 columns a row's first press acts too, not only focuses its list (`app/mouse.rs` `press_acts`). `app/mouse_tests.rs` drives the list through `TestApp`.
  The phone (probe, 2026-11-27) sends a tap as a press and its release at one cell and a swipe as wheel codes with no drag; `app/mouse_tests.rs` `a_logged_*` feeds those bytes through `TestApp`.
- **Dotfiles are a row filter, not a listing filter.** `Tree::rows` skips a dot entry and its children while `Tree::dotfiles` is off; the listing keeps them, so a toggle reads nothing. The noise list is dropped at the read (`fs::read_entries`), so it stays hidden in both states. The finder's index is the one walk that does read again (`app/find.rs` `reindex`).
- **Widths come from the native measure.** Footer fitting measures with `Context::text_width` and the app's width method, so `↑`, `…`, and wide characters count as the terminal draws them; tests pass a character count.
- **The changes body is measured by the frame.** Block tops and hunk rows come from the laid-out blocks (`ui/diff.rs` `tops` and `hunk_rows`), so a jump to a file waits up to `JUMP_TRIES` paints for the layout (`app/changes.rs` `jump`). The list follows the body only from the body's own scroll event (`app/mod.rs`, the stack's `on_scroll`), as Scouter's `layoutChanged` does; a repaint alone never moves the selection.
- **A list keeps its wheel scroll across repaints.** `ChangeList::set_height` only clamps the scroll: the selected row is brought into view by a new listing and by a selection move. A repaint that scrolled to the selection would undo each wheel notch on the next frame (`diff/list.rs`). The tree's `Browser::set_height` follows the same rule at an unchanged height; a new height (the first layout, a resize) brings the selection into view (`explorer/browser.rs`, plan-00001 phase 23d).
- **The body's build key names the listing.** `ui/diff.rs` `Key` is the session, the generation, the gutter digits, and the color mode. A generation counts from zero on each visit, so without the session a later visit could reuse the blocks of an earlier one.
- **The stacked body is as wide as the pane, or as the widest line of its unfolded diffs needs, and every header takes that width.** A diff's need is its line-number digits, the gutter's four cells, and its widest line after the sign (`ui/diff.rs` `block`, `diff/stack.rs` `widest_line`). `ui/diff.rs` `apply_widths` takes the stack from `stack_columns` over the shown diffs: a folded block, a notice, and a wrapped body do not widen it. While a line overflows, a header's counts and stat bar sit past the pane edge until a pan reveals them (architecture.md, "a diff fits the pane when its lines do"). `ui/diff_tests.rs` pins the widths on a frame.
- **The stacked body's pane is one column wider while its bar is hidden.** The bar takes a column only while the stack overflows (`ui/scrollbar.rs`), so `paint` sets the pane from `ui.diff.height() > viewport`; a fixed pane leaves a blank column in one-file view (Scouter's scroller reserves its bar only when the text overflows).
- **The listing and its patches share one repository.** `services/changes.rs` `list` returns the `Repository` with its listing, shared as an `Arc`; the patches read that repository's copy of the index, so they run after the listing on the same repository, as Scouter's `loadAll` follows `load`.
- **The compact bars are the footer's one row and the header's back chevron.** `ui/bars.rs` holds the bottom bar's segments per page (`page_segments`), their equal cells (`cells`, one `·` column between them), and the prompt bar (`Cancel` in the first cell, then the prompt's text). `FooterState::bar` draws it; `Footer::paint` makes the footer one row and hides the band below 60 columns. A tap on a cell presses the segment's key through `app/keys.rs` `hint_presses`, as a footer hint does. The compact back chevron is `PaneHeader`'s lead cell: `pages::back_lead` gives `‹` over any page but Files, and `app/layout.rs` `wire` makes a press there call `pages::back`. The same cell holds the medium chevron, so the press checks `back_lead` and then the chevron before it stops the press.
- **A visible child takes a share of its stack.** The stack's children split its height by grow, hidden ones take none, and the reader's viewer is shown only while a document is open (`src/app/mod.rs` paint, `ui.viewer.visible`). A visible empty viewer halves the stack, and the welcome inside its half clips at 80x24 (issue-00004, fixed in plan-00001 phase 23a). A rebuild that re-adds a child moves it to the end of the stack, so it sits behind the siblings above it.
- **Search marks number a build, so a build restarts the count.** `ui/markdown_search.rs` numbers each prose piece (`Paint::prose`) and each code block (`count_code`) as OpenTUI builds it: the inline hook and every code renderer count their calls, and the offscreen index numbers the same way, block by block. `MarkdownView::show`, `apply`, and `mark` restart the count and rebuild the document, because a block whose text is unchanged keeps its widget and is not built again. A new code-block renderer calls `count_code` first, the diagram renderer included, or the numbers drift.
- **A block's document top comes from the heights, not from `block_rows`.** `block_rows` clamps a block above the view to row 0 (`screen_y.max(0.0)`) but keeps its height, and blocks stand one row apart, so `MarkdownView::block_tops` sums `end - start` and adds one per block. It is empty until a frame lays the document out, so a jump waits for it.
- **The rendered view's sign column waits for a layout.** `ui/markdown_signs.rs` places each mark at its block's top less the scroll, as absolute widgets in the viewer's row, at each paint. `MarkdownView::block_tops` is empty until the document has a height (before the first frame every block is zero rows), so a paint before the layout places nothing, and the app repaints 20 ms after each layout (`repaint_after_layout`). A test that paints must paint again after its render, as `app/rendered_signs_tests.rs` `reading` does.
- **An injection query compiles with its grammar, and a bad one drops the grammar.** `ui/syntax/mod.rs` `injected` gives each `queries/<filetype>/injections.scm` to `Grammar::injections`, and OpenTUI compiles it with the highlights (`opentui-0.9.9/src/syntax/highlight.rs:246-255`). A node name the grammar does not have makes the whole grammar fail, so the file shows plain; `every_vendored_grammar_compiles_with_its_query` catches it. An injection's language is resolved by name, and a name that is not registered is skipped (`highlight.rs:383-410`), which is how the Elixir `~VUE` rule stays inert.
- **Core's cascade paints a 2-part host capture over the injected text.** Captures are ordered by fewer dotted parts first, then by start (`highlight.rs`, `highlights`), and the later one paints, so a host `string.special` covers an injected `tag` or `keyword`. A host rule over injected content leaves that content out: `queries/elixir/highlights.scm` does it for the injected sigils (plan-00013; `architecture.md`, "an injected sigil's body is left to its injection"), and the JavaScript, TypeScript, and TSX queries do it for regex patterns and `/** */` comments (`architecture.md`, "JavaScript, TypeScript, and Python code inside a file is highlighted"). Those files and the Elixir one differ from their Core or crate copies by these rules, so a fresh copy needs them again.
- **A colour is a `Hex`, and a palette is a value.** `theme::Hex` is seven ASCII bytes (`#rrggbb`, lowercase), so a palette read is a copy: `Seg.fg` and `Seg.bg` are `Option<Hex>`, and the views take `Hex` where a colour is passed. A built-in value is `Hex::new` in a `const` (a bad literal fails the build); a file's or the catalog's value is `Hex::parse`, which returns `None` on a bad one. `Hex` derefs to `str` for the engine's `color`. The palettes are owned: the Model keeps the dark and the light palette it chose (`app/mod.rs` `Model::palette`), and a user theme is a value, never a leaked `&'static str` (plan-00015, A5 as amended by A15). A view that holds the palette across a write copies it first, as `paint` does.
- **One subprocess runner.** `services/mod.rs` `capture` runs git and the launcher: argv only, stdin null, a 15 s timeout, a capped output, and an error that names the program (`git exited with status 3.`, `/usr/bin/open exited with status 1.`). A new subprocess calls it; it does not start its own reader loop.
- **A menu's rows are indexed for the whole menu.** `Menu::pick` and `Menu::point` take the index in `items`. The view's row widget at slot `n` is item `top() + n` (`app/overlay.rs` `wire_views`). Passing the slot selects the wrong row once a menu scrolls.
- **A late picker is dropped.** `Event::Apps` opens the Open With picker only while its target is still the target (`app/open.rs` `listed`). A listing that lands after the selection moved is ignored, so a picker never opens for a file the user has left.
- **One pattern table.** `reader/associations.rs` `Patterns<T>` holds `file_associations` (`Associations`) and `open_with` (`OpenWith`), and both pick the winning pattern in `winner`. A change to the precedence moves both tables, which is the point.
- **A vendored grammar's C symbol is unique, and its wrapper is one unsafe cast.** `build.rs` compiles each `vendor/grammars/<name>/src/parser.c` (and `scanner.c` where present), and `src/ui/syntax/vendored.rs` declares its `tree_sitter_<name>` symbol. Two crates that export one symbol cannot link into one binary: `tree-sitter-tsquery` and `konomanoasa-tree-sitter-query` both export `tree_sitter_query`, so only the first is a dependency. `tree-sitter-language` is not a direct dependency, so `LanguageFn` cannot be named; `vendored.rs` `language` transmutes the function pointer into it, which holds because `LanguageFn` is `repr(transparent)` over that pointer type (`tree-sitter-language` 0.1.9, `src/language.rs`).
- **A menu's group rule needs rows before it.** `open.rs` `listed` sets `rule` on a row only when rows came before it, so an empty group (no configured apps) leads with no separator.
- **A lone image is one fence whose info string carries it, and every line keeps its number.** `ui/markdown_images.rs` `as_boxes` turns a top-level paragraph that is one image into a `fmc-image` fence: its line moves into the info string and the blank line after it becomes the closing fence, so no line is added. A fence cannot sit on one line, so a paragraph with no blank line after it, or a backtick in it, keeps its text. An HTML block that is one image (`reader/images.rs` `parse_html`, the tags read by `reader/html.rs` `tags`) takes the same rewrite: its lines join into the info string, its lines between the first and last stay as the fence body, and its last text line closes the fence (a one-line block closes on the blank line after it). tree-sitter-md takes that blank line into the block, so `as_boxes` ends the block at its last text line. The renderer reads the image back with `reader/images.rs` `from_info` (`parse_source` reads either form), which is why the info string holds the whole source.
The box's renderer counts its fence with `count_code` first, as the code renderers do, and `register_capture` registers `fmc-image` on the offscreen search index too, so the slots of a search and its count hold with a box in the document (`ui/markdown_search.rs` `capture_code`). A search finds a box by its name, which the index records from `reader/images.rs` `from_info`.
- **A restored scroll waits for a paint.** A document shown again is laid out after the show, so a scroll set in the show is clamped to the rows drawn before. `app/reader.rs` `reset_scroll` sets `pending_top` (the paint applies it until it holds or `OPEN_SCROLL_TRIES` runs out), as the search's open does. The `m.top` the jump history records lags a key press, so a jump takes the viewer's position at the moment it opens (`app/picture.rs` `open`).
- **A box does no I/O: its header comes from a worker and is set on the view.** `app/picture.rs` `request` asks `services/picture.rs` for each box's header when a Markdown text shows, and `apply` keeps the answer only for the showing it was asked for (`Shown::Text` path and serial). `MarkdownView::show` clears the headers, since they name the last document's folder; `set_headers` rebuilds the document so the boxes draw them. The header cache is keyed by the canonical path and the file's modification time, so an unchanged image is not read again.
- **A picture is decided at each build, from the cache, and decodes once on the UI thread.** `ui/markdown_pictures.rs` `widget` returns the `ImageView` of a decoded picture, else the box: the cache (`Pictures`, 32 entries by path and modification time) answers, and a miss draws the box at the picture's rows. The bytes come from a worker (`app/picture.rs` `apply` asks for `MarkdownView::wanted`, `Event::PictureBytes`), and `MarkdownView::decode` decodes them on the UI thread, since the native context is not `Send` (`opentui-0.9.9/src/native/context.rs:31`). A decode that fails is kept as the box's reason, and a picture is not read again for the same modification time. The renderer reads the cache and the theme's source (`reader/images.rs` `target_for`) and nothing else, so a rebuild does not decode.
- **A picture's size is explicit columns and an aspect ratio, set at each build.** `Size::apply` (`ui/image_box.rs`) sets the width in columns and the height from the ratio, capped at `row_cap` (three fifths of the viewer's rows). The columns are the natural width (pixels at `reader/images.rs` `CELL_WIDTH`) clamped to the text's width, which `MarkdownView::fit` takes at each paint (`app/mod.rs`), so a resize rebuilds the document once. Layout does not stretch a box to the pane: a `max_width` with no width was ignored in the spike, and a percent of the document's block is not defined.
